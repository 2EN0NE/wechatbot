# 桥的观测策略：日志为唯一真源，阈值跨越事件而非定时采样，告警不占微信通道

日志已有 21 类事件（`message received` / `sent turn to pi` / `reply sent` / `replayed turn from journal` / `inactivity timeout notified` / `message dropped — …` / `failed to send turn to pi after retries` …），事件级真相基本齐全。缺的只有三样：队列深度（状态量，不是事件量）、深度阈值跨越（堆积到几条毫无记录）、以及 journal 的 admit / settle 可见性（只在出错时记 `journal error`，正常准入与结算零日志——而"这轮 admit 到底有没有落盘"正是 Replay 验证最需要的证据）。

决策三条：

1. **不新增持久化 metrics 文件。**（进程内的计数器模块 `src/metrics.ts` 不属于此列：它不落盘、不构成第二真相源，只是下面这句「`/status` 暴露进程内累计计数」的实现。）日志是持久真源，`/status` 暴露进程内累计计数（`admitted / settled / replayed / dropped / stalled`）。进程内计数重启归零是刻意的——它只是"当场看一眼"的便利，事后追溯一律靠 grep 日志。
2. **队列深度只记「跨越阈值」事件**（向上越 3、越 10 各一次，归零一次 INFO，事件带深度值），不做定时采样。深度是状态量，记跨越事件的成本是 O(事件数)，采样是 O(分钟数)，而 `grep` 对前者天然友好。
3. **告警不占微信通道。** 停滞判据完全复用 ADR-0006（不活跃超时 + 每轮至多一次通知），不新增墙钟判据；队列越界不推微信，只记日志。

为什么队列深不能当告警：桥无法区分「pi 在努力跑长任务」和「pi 卡死」（ADR-0006 已论证——扩展拿不到"等待权限确认"事件）。一次 agent run 本来就可能几分钟，期间用户连发 5 条完全正常。再加一个"深度超阈值且持续 M 秒"的墙钟告警，一是与 ADR-0006 判据重叠并打架，二是必然产生噪音。真正的卡住已被不活跃超时覆盖。

为什么微信侧零新增告警：桥的诊断信息只有两类消费者——事后 grep 的人，和当场看状态栏的人。前者要事件日志，后者要 `/status` 计数。微信推送面向的是"需要采取行动的第三方"，而这一类不存在：用户收到"你的 bot 有点忙"唯一能做的就是 `stop`，而真正需要他行动的情况，ADR-0006 已经通知过一次。

**这是一个刻意偏离直觉的选择**：未来若要加 metrics 文件或微信告警，先重读本 ADR——两者都是"看似合理"的动作，前者制造第二真相源（必然与日志漂移），后者稀释 ADR-0006 的通知价值。

触发重评的条件：出现"需要跨会话统计趋势"的真实需求（例如要判断桥多久卡一次）。届时形态应是 journal 同族的追加式 JSONL 事件流，而不是一个新的 metrics 文件格式。
